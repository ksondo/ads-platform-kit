### How RCK code is shaped (applies to every row)

- **Frontend:** modules call `corestack.from('<table>')` through `src/platform/sectorApiCompat.ts`. This is a Supabase-shaped query builder that posts table operations to `/api/sector-gateway` (`api/sector-gateway.ts`, `server/sector-api*.mjs`). Porting means replacing every `corestack.from/rpc/functions.invoke` with a versioned product API.
- **Sign-in:** `src/contexts/AuthContext`, `ProtectedRoute.tsx`, `Login.tsx`, `MerchantLogin.tsx`, `ResetPassword.tsx`, `server/corestack-identity.mjs`, `deploy/postgres/004_corestack_identity.sql` and `src/integrations/lovable` (Lovable OAuth) are product-own logins. **Do not carry over.** Use the kit (`packages/identity-client/ads-identity.js`, `services/identity`, PLAT-ID-001).
- **Database on M@:** `deploy/postgres/003_all_sector_persistence.sql` creates generic `sector_<x>.providers/offerings/journeys` for 17 sectors. The real domain tables (`tour_*`, `mobi_*`, `diaspora_*`, `construction_*`, …) exist **only** as Supabase migrations at S@.
- **Tests:** RCK has 25 test files on M@, but none for tourism, mobility, diaspora, banking, construction or process, apart from `services/tourism/tests/boundary.test.mjs` (an 11-line stub check). At S@ the only banking-adjacent tests are `supabase/tests/transaction_processing_auth.ts` and `transaction_processing_vat.ts`.
- **Service stubs:** `services/<sector>/service.mjs` (3-line HTTP stubs answering 501) exist for 12 sectors. `services/tourism` and `services/health` add `contracts/public-api.ts`, `deploy/*` and one boundary test. All have `deployableIndependently: false`.

## 2. Transfer manifests for the three new repos

Common rules for all three:
- **Copy with provenance.** Put the copied files under `imports/retail-connect-kit/<original path>` (reference, not built) and add `docs/migration/RCK_SOURCE_POINTER.md` naming the commit (M@ `47b3c07a7a18` or S@ `25962b65ac72`) and each original path. This is the pattern Fleet Guard and logistics already use. Requirements docs go under `docs/requirements/rck-source/<same sub-path>`, unchanged.
- **Rewrite, don't run.** Do not run the copied code. Rewrite it into the repo's own stack: Node server + PostgreSQL `db/migrations`, row-level security using server-set actor settings (pattern in education `018_governed_school_finance.sql`), and versioned REST under `/api/v1/...`.
- **Supabase → PostgreSQL.** Replace every `corestack.from/rpc/functions.invoke` (`sectorApiCompat`) with typed API clients. Turn Deno Edge Functions into server routes. Drop `auth.uid()` policies, `SUPABASE_*` env and the service-role pattern. Use idempotency keys on writes. No cross-repository foreign keys; use opaque references.
- **Sign-in → kit.** Replace `AuthContext`, `ProtectedRoute`, `OperatorGate` and `verify_manager_pin` with kit `ads-identity.js` on the client and token, role and tenant checks on the server (PLAT-ID-001, PLAT-ROLE-001). Manager approval becomes a server-side approval, as in commerce `025_pos_roles_manager_approval_offline.sql`.
- **External parties → kit mocks** (PLAT-EXT-001): payments `momo`, `bank`, `kyc`; notifications via PLAT-NOT-001; payments honest-state rules from PLAT-PAY-001.
- **Never copy:** demo passwords, seeders, `remotion/`, workflows, `scripts/gate0-*`, `.lovable/` (except as quoted provenance).
