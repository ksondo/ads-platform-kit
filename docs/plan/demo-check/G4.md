- **Check:** one Playwright (1.56, Chromium) script outside the product repos, driven by a small per-product config. For each product it:
  1. Opens the product and clicks its Sign in button.
  2. On the kit sign-in page, checks that the demo panel is shown and clicks **Use demo account** (the field fills with `demo.user@demo.africadigitalsynergy.com`), then clicks Continue.
  3. Picks the product's demo organisation on `/choose-workspace`, and checks the browser returns to the product signed in.
  4. Opens the role home and the key screens, and takes one role-home screenshot.
  5. Repeats with the staff organisation, where the demo user holds staff roles.
  6. Signs in as the **demo admin** (typed credentials, because the panel never shows the admin) and opens the admin or staff screen.
  7. Signs out each time.

  A screen counts as FAIL if it shows a denied or error message. It counts as PARTIAL if it renders but a product API call on it returns 4xx/5xx.

## Per product: what the demo host must set, and fixes

### Agriculture (`agriculture-web`)
- **Env:** `OIDC_ISSUER`, `OIDC_AUDIENCE=agriculture-web`, `OIDC_JWKS_URL`, `ADS_IDENTITY_URL`, `ADS_IDENTITY_CLIENT_ID`, `ADS_MOCKS_URL`, `ADS_MOCKS_WEBHOOK_SECRET`, `EXTERNAL_MODE=mock`, `PUBLIC_URL`, `CALLBACK_BASE_URL`, `AGRI_PARTNER_AFRICOVER_SECRET`, `PORT`.
  - `DATABASE_URL` must be a restricted login that is a member of `agri_app`/`agri_worker`. The server refuses the owner or a superuser.
  - Migrations run with `MIGRATION_DATABASE_URL`, using a login that can create roles.
  - The server reads no client secret. `client_secret_setting: null` in `clients.demo.json` is correct, so the generated secret is unused.
- **Operator setup:** `npm run admin -- add-staff-tenant <staff tenant> "ADS staff"`.
- **Fix (small):** `src/admin.mjs` add-staff-tenant fails with `inconsistent types deduced for parameter $1`. The command reuses `$1` for `audit_events.tenant_id` (uuid) and `resource_id` (text), so the audit insert fails and the command exits 1. The staff row is still saved because there is no transaction. Suggested change: pass the tenant twice (`VALUES($1,'operator',…,'staff_tenant',$2,$3)` with `[tenant, tenant, {label}]`) or cast it (`$1::text`), and wrap both inserts in one transaction.

### HopeBridge (`hopebridge-web`)
- **Env:**
  - Identity: `OIDC_*`.
  - Build-time: `VITE_ADS_IDENTITY_URL`, `VITE_ADS_CLIENT_ID`, `VITE_ADS_REDIRECT_URI`. The web app is built per host, and these values are baked into the bundle.
  - App: `STATIC_DIR=dist`, `ALLOWED_ORIGINS`, `PUBLIC_CALLBACK_BASE_URL`, `EVIDENCE_STORAGE_ROOT`.
  - Partners: `PARTNER_MODE=mock`, `HOPEBRIDGE_PARTNER_MOCKS_URL` and `PARTNER_MOCKS_WEBHOOK_SECRET` (run `server/mocks/test-mode-partners.ts`).
  - Mocks: `ADS_MOCKS_URL`, `ADS_MOCKS_WEBHOOK_SECRET`.
  - `ADS_ADMIN_CLIENT_SECRET` (the setting name in `clients.demo.json` is right).
- **Cause of the failure:** `server/identity.ts` (`resolveSession`) keeps only token roles that HopeBridge also grants. Those are memberships in a HopeBridge organisation whose `ads_tenant_id` matches the token tenant, plus `public.user_roles`. `demo-orgs` creates only the ADS organisations and roles, so every staff screen is denied for the demo user and the demo admin.
- **Seed that made it pass:** run after the demo accounts have signed in once, because HopeBridge creates `app_identity.users` on first sign-in.

  ```sql
  insert into public.organisations(name,organisation_type,status,ads_tenant_id)
    values('ADS Demo – NGO','licensed_ngo','active','<hopebridge main tenant>');
  -- demo user: every main-org role in clients.demo.json except community_user (ngo_operations … donor)
  insert into public.memberships(user_id,organisation_id,role,status) select u.id,o.id,r::public.app_role,'active'
    from app_identity.users u, public.organisations o,
    unnest(array['ngo_operations','case_worker','programme_officer','eligibility_officer','approver','referral_officer',
                 'finance_viewer','safeguarding_officer','me_officer','partner','donor']) r
    where lower(u.email)='demo.user@demo.africadigitalsynergy.com' and o.ads_tenant_id='<main tenant>';
  insert into public.memberships(user_id,organisation_id,role,status) select u.id,o.id,'ngo_admin','active'
    from app_identity.users u, public.organisations o
    where lower(u.email)='demo.admin@demo.africadigitalsynergy.com' and o.ads_tenant_id='<main tenant>';
  insert into public.user_roles(user_id,role) select id,'platform_admin' from app_identity.users
    where lower(email)='demo.user@demo.africadigitalsynergy.com';   -- staff org (platform_admin)
  ```

- **Fix (suggested code addition, not made):** add an operator command, for example `scripts/ops/demo-seed.mjs` or `npm run hb-admin -- link-org <tenant> "<name>" --members <email:role,…>`. It would link an ADS organisation and pre-create users by verified email and `ads_subject`, so the seed does not depend on a first sign-in. Alternatively, make `demo-orgs` emit a HopeBridge seed. Also add `public.user_roles` `platform_admin` for the staff-org user.
- **Minor:** signed in to the staff organisation as `platform_admin`, `/cases?view=verification` renders, but `GET /api/v1/appeals` and `GET /api/v1/follow-ups` return 403. Either the view should not call them for this role, or the API should allow them.

## What the demo host setup must contain (from this run)

1. `register-client` (and so `apply-clients`) accepts only `https://` URIs or `http://localhost`. Local runs must use `http://localhost:<port>/`, not `http://127.0.0.1`. The `*.test.africadigitalsynergy.com` URIs in `clients.demo.json` are fine for hosting.
2. `demo-orgs --clients <file>` must use the same client list as `apply-clients`.
   - Pass the `staff_tenants`/`settings` from the output file to `TOUR_PLATFORM_TENANT_ID` and `BANKING_OPERATOR_TENANT_IDS`.
   - Run the operator setup commands: Agriculture `add-staff-tenant`, Software Factory `register-staff-org`.
3. Add product-side demo seeds where a product keeps its own organisation records:
   - **HopeBridge:** organisation link and memberships (above).
   - **Banking:** a partner bank for the demo organisation (above).
4. Optionally, add sample catalogue data so screens are not empty. This would help Tourism, Transport, Investment and Agriculture.
5. Every product needs its own test-mode partner mocks besides the kit mocks:
   - VentureWorks double for Investment
   - partner mocks for HopeBridge, Transport and Software Factory
   - POS and Settlement mocks for Tourism
   - bank mocks for Banking
6. HopeBridge's web bundle must be built per host, because `VITE_ADS_*` values are compiled in.
